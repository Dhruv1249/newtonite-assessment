# OpFlow - Architectural and Engineering Decisions

This document details five fundamental architectural decisions made during the design and
implementation of OpFlow for the Newtonite Software Engineering Challenge, including the
evaluated trade-offs, rationale, and documented deliberate omissions.

---

## 1. Optimistic Concurrency Control with Monotonic Version Vectors

### Context and Problem
In operational pressure environments, multiple operators frequently view and interact with the same
work item simultaneously. When two operators attempt to transition an incident, reassign an owner, or
update remediation notes simultaneously, naive last-write-wins patterns silently overwrite historical context
and critical updates. Conversely, pessimistic locking (e.g. database row locks or distributed Redis mutexes)
introduces severe operational risks: abandoned locks when an operator closes their browser tab, lock contention,
and potential distributed deadlocks.

### Architectural Solution
We implemented Optimistic Concurrency Control (OCC) using a monotonically increasing integer `version`
column on the `work_items` table.
- Every mutating endpoint (`PUT /api/v1/items/{id}`, `POST /api/v1/items/{id}/transition`, `POST /api/v1/items/{id}/assign`)
  requires the client to provide the `expected_version` they were viewing.
- The service layer performs an atomic conditional update:
  ```sql
  UPDATE work_items
  SET status = :target_status, version = version + 1, updated_at = :now
  WHERE id = :item_id AND version = :expected_version;
  ```
- If zero rows are affected, the database transaction identifies that a concurrent mutation occurred. The server
  rejects the request with `HTTP 409 Conflict` and returns a descriptive error payload.
- On the frontend, TanStack Query catches the 409 status and renders a non-destructive `ConflictDialog`,
  prompting the operator to refresh the latest server state without losing their local input context.

### Trade-offs
- **Advantage**: Zero locking overhead, non-blocking reads, immune to abandoned browser locks.
- **Cost**: Requires frontend clients to track version numbers and present resolution workflows when conflicts arise.

## 2. Unified Storage: PostgreSQL 17 with pgvector vs. Standalone Vector Databases

### Context and Problem
OpFlow requires standard relational capabilities (multi-team memberships, role hierarchies, foreign key constraints,
audit logs) alongside high-dimensional vector representations for semantic search and duplicate item detection.
Industry frameworks frequently mandate external vector stores like Pinecone, Weaviate, or Milvus.

### Architectural Solution
We chose a unified database architecture using PostgreSQL 17 with the native `pgvector 0.8.7` extension.
Work items store their dense 3072-dimensional vector embeddings generated by `gemini-embedding-002` directly in
an `embedding` column on the `work_items` table.
- Semantic similarity is computed directly in SQL using the cosine distance operator (`<=>`):
  ```sql
  SELECT id, title, (1.0 - (embedding <=> :query_vector)) AS similarity_score
  FROM work_items
  WHERE team_id IN (:accessible_teams) AND embedding IS NOT NULL
  ORDER BY embedding <=> :query_vector
  LIMIT 15;
  ```

### Trade-offs
- **Advantage**: Eliminates distributed synchronization drift between a relational database and a separate vector store.
  Enforces multi-team resource authorization directly in the same SQL query as the vector similarity calculation.
  Single container deployment without extra network hops or independent point of failure.
- **Cost**: Dedicated vector databases scale better past tens of millions of items. However, for the target scale
  (tens of thousands of active work items with hundreds of concurrent users), PostgreSQL with pgvector provides
  sub-5ms retrieval latency with complete ACID safety.

## 3. Synchronous Core State vs. Resilient Database-Backed Asynchronous Task Queue

### Context and Problem
Generative AI calls (embedding generation, duplicate triage, and LLM reasoning) require between 400ms and 2500ms
and are subject to external API rate limits or transient latency spikes. Executing these calls synchronously in
the work item creation path would severely degrade API responsiveness and cause primary creation failures whenever
an upstream AI provider experiences transient degradation.

### Architectural Solution
We separated primary operational mutations from secondary intelligence enrichment:
- **Synchronous Path**: Creating a work item, logging its audit record, and returning the created entity
  executes synchronously within a single transaction in sub-10ms.
- **Asynchronous Path**: An entry is placed into a durable `task_queue` table with task type `generate_embedding_and_triage`.
  A background worker executes the task, generates embeddings via `gemini-embedding-002`, performs duplicate
  detection, and generates triage metadata using `gemini-3.1-flash-lite` (with automatic failover to `gemini-3.5-flash-lite`).
- **Resilience Guarantees**: Tasks track execution `attempts` with a maximum limit of 3. Stale tasks stuck in
  `processing` status for greater than 5 minutes due to unexpected worker restarts are automatically reclaimed to `pending`.
- **Client Notification**: Once enrichment completes, the worker broadcasts an `item_enriched` notification over
  Server-Sent Events (SSE), prompting connected browsers to invalidate their cache and render suggestions.

### Trade-offs
- **Advantage**: Fast user experience on critical paths; operational work items can never be blocked by third-party AI outages.
- **Cost**: Eventual consistency for AI suggestions (typically visible within 1-2 seconds of creation).

## 4. Resource-Level Authorization Enforced at the Query Boundary

### Context and Problem
In a multi-team company, authorization cannot be implemented solely by hiding controls in the user interface or by
coarse global user flags. An engineer in Platform Engineering must have write access to infrastructure items but
strictly read-only or zero visibility into confidential security audit requests in Compliance & Security.

### Architectural Solution
We implemented a multi-layered authorization model:
1. **Query-Level Scoping**: All work item queries automatically resolve the caller's active team memberships and
   filter at the SQL boundary (`WHERE team_id IN (:user_team_ids)`). An unauthorized item cannot be leaked through
   list views, global searches, or direct ID lookups.
2. **Team-Scoped Roles**: Roles (`admin`, `lead`, `member`, `viewer`) are defined per-team in `team_members`.
   - `viewer`: Read-only access to work items, comments, and history. Cannot create, edit, or transition items.
   - `member`: Can create items, edit assigned items, and submit items for review.
   - `lead`: Can assign items, triage, and execute review/approval transitions.
   - `admin`: Full team administration, membership enrollment, and workflow modification.
3. **Workflow Role Guards**: Permitted transitions in the team's workflow specification declare `required_roles`.
   The `WorkflowEngine` verifies that the actor holds the required role before allowing any state change.

### Trade-offs
- **Advantage**: Enforced at the lowest layer of the backend; impossible to bypass by crafting direct HTTP calls.
- **Cost**: Every request performs role resolution, requiring indexed lookups on `team_members`.

## 5. Idempotent Operations via Client Deduplication Keys

### Context and Problem
Under high-pressure operational situations, users repeatedly press submit buttons when encountering perceived network
latency. Without idempotency, duplicate incident records or duplicate approvals are created, fragmenting team communication.

### Architectural Solution
Mutating endpoints accept an optional `Idempotency-Key` HTTP header.
- Before executing creation logic, the server checks the `idempotency_keys` table for the pair `(key, user_id)`.
- If an existing entry is found and unexpired, the server immediately returns the cached `status_code` and `response_body`
  without executing duplicate database inserts or background tasks.
- If no entry exists, the mutation executes, and the final response payload is persisted with a 24-hour expiration timestamp.

### Trade-offs
- **Advantage**: Guarantees exactly-once creation semantics even across network retries and impatient user clicks.
- **Cost**: Introduces a dedicated lookup table and slight serialization overhead on idempotent endpoints.

## Deliberate Non-Goals (Scope Discipline)

To deliver a reliable, fully-functional system within the one-day constraint, the following elements were
intentionally not built:
1. **Visual Drag-and-Drop Workflow Canvas**: Built a structured form-based inspector and editor instead. This
   demonstrates 100% of the workflow enforcement engine and role-guard logic without spending hours debugging
   canvas rendering and edge routing.
2. **Bidirectional WebSockets**: Selected unidirectional Server-Sent Events (SSE). SSE operates over standard HTTP/2,
   reconnects automatically, and avoids complex WebSocket handshake, connection pool, and heartbeat management
   while delivering instantaneous cache invalidation to clients.
3. **Outbound Email and SMS Gateway**: External email delivery is replaced by real-time in-app SSE notifications
   and chronological activity logs to avoid external SMTP dependencies.
